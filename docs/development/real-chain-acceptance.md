# 真实链路验收

目标：固定镜头、单只猫，验证采集 → 检测 → 四态 → SQLite → 网页 → 断流恢复。双猫不输出单猫活动/休息；当前 C++ 不提供 coco/kui 持久身份。本文为待执行验收流程，不是板端通过记录。

## 1. 先验证前台服务

按 cpp-runtime.md 在板端构建 TensorRT 运行时并准备目标设备的 engine。使用独立数据目录，先运行 2 小时。保留 source/model 在私有配置中，不提交地址或账号。API 继续绑定回环地址；电脑查看需已有 SSH 端口转发。

运行验收工具（与 API 同机，或经转发）：

```bash
python3 scripts/verify_runtime.py --seconds 7200 --output local/acceptance/two-hours.json
```

默认要求 `mode=live`，且至少观察到一次新鲜的在线推理；全程离线不能通过。验证工具只读当前状态及每五秒一份当天时间线；不保存图像、来源名称或接口地址。报告在被忽略的 local 下。API 超时、字段异常或时间线错误导致非零退出。

它记录 API P95、不同序号的推理耗时 P50/P95、丢弃帧数增量、序号重置和过期观察。计数来自抽样，不是行为时长、真实 FPS、完整推理性能或准确率。单帧邮箱丢弃是主动防积压，不等于网络丢包。没有温度、功耗和内存测量能力，需另行使用板端工具记录。

## 2. 断流恢复

在服务保持运行的前提下，对视频源人为断流至少 10 秒，再恢复。不要关闭 HTTP 服务或数据库。启动监控后先确认在线，再操作：

```bash
python3 scripts/verify_runtime.py --seconds 180 --require-recovery --output local/acceptance/recovery.json
```

通过条件是抽样到新鲜在线 → 离线 → 新鲜在线，且 API 与时间线契约无错。没有观察到完整顺序会失败，不从最终在线状态推断恢复成功。数据应显示断流为 offline，不能填成休息。此检查不能替代浏览器视觉核验或准确率评估。

## 3. 重启与日边界

- 服务停止前保存当天时间线；重启使用同一个数据库，确认已提交区间仍在。
- 重启空档应为 unknown，不能延长之前的活动/休息。
- 数据跨 UTC 午夜时分别查两天，总时长不能重复累计。
- 消费者页面按浏览器时区统计本地一天；验证本地午夜前后的区间裁剪，存储时间仍为 UTC。
- 回归测试覆盖区间持久化、重复时间与日边界；真实设备仍需执行。

## 4. 准确性样例

第一轮人工记录每种场景至少三次：正面、转身、椅子遮挡、远处、暗光、抱猫、两只猫、猫离开视野。记录预期、输出、持续时间和失败原因，放在 local/acceptance；采集媒体须由用户主动决定。

分开评估检测是否找到猫、短期轨迹是否稳定、活动规则是否正确。unknown 是证据不足，不能为了减少 unknown 调低所有阈值。resting 是低位移，不是确认睡眠。没有标注样本前不报告准确率。

## 5. 后台服务准备

前台 2 小时及断流通过后，再考虑 12 小时和一天运行。`deploy/systemd/coco-context.service` 是尚待板端核验的用户服务模板，没有在本机或板端安装启用。

构建安装位置约定为 `~/.local/coco`，网页在 share/coco/web，数据库在 `~/.local/share/coco/context.db`。私有文件 `~/.config/coco/context.env` 提供 `COCO_SOURCE`、`COCO_MODEL`、`COCO_BACKEND`（tensorrt/onnx）；这些变量是 systemd 环境文件格式，不是执行 shell 脚本。环境文件和状态目录限制为当前用户访问。模板重启失败程序，但五次启动失败会停下，防止无休止报错。

用户服务与开机前登录的运行方式不同；是否启用 linger 或改系统服务，要在明确日常使用方式后决定。不在本轮自动修改系统设置。

## 下一次需要决定的事项

首次真实验收已选固定 CSI。长时间验收结束前保持进程和版本不变，结果写入私有 local 目录。

后续需要决定个人远程使用先采用私有访问还是建设账户网关；后者还需选择托管方式，不能直接公开本地 API。

## 本地日统计接口

`GET /v1/context/current` 的 `timeline_window_supported: true` 表示支持显式日窗口。旧版客户端仍可查询 `GET /v1/timeline?day=YYYY-MM-DD`，按 UTC 零点统计。

本地日查询为 `GET /v1/timeline?day=YYYY-MM-DD&start=UNIX_SECONDS&end=UNIX_SECONDS`。客户端把本地零点和次日零点转换成 UTC 秒；两端点必须同时提供。服务端检查日期、重复或未知参数、整数溢出，以及窗口范围：起点距日期的 UTC 零点不超过 14 小时，窗口长度为 22–26 小时。错误请求返回 400。

响应新增 `window_start`、`window_end`（UTC 时间）和 `day_seconds`（完整日长）。区间和汇总仍仅统计到当前时刻，不把未来时间填成 unknown。非 UTC 窗口的 `timezone` 为 `window`，不推断具体 IANA 时区；显示时区由客户端确定。网页旧版设备回退到 UTC，并明确标注，避免统计口径与时间显示不一致。

自动回归覆盖 UTC 与本地午夜裁剪、23/25 小时的夏令时日期，以及无效窗口参数。板端部署要等待正在运行的验收结束。

## 漏检缓冲验收

四种业务状态保持不变；`unknown` 表示证据不足，`pet_evidence` 提供观察阶段。单只猫已有确认轨迹后，最后可靠观测后 3 秒内的漏检保留最近活动决策（held），3–8 秒进入 unknown/searching，超过 8 秒且在席状态确认缺失后进入 out_of_view/absent。没有可靠历史不会凭空保留；多猫立即进入 ambiguous，不复用单猫判断；摄像头离线优先于所有缓冲。

`pet_last_seen_seconds` 是距最后可靠猫咪检测的秒数，区别于整帧推理新鲜度。猫咪恢复到确认轨迹后改为 observed；新轨迹未确认时显示 confirming，不能据此延长保留窗口。统计层将 held 写为 unknown；检测数量、轨迹框仍来自实际检测，保留动画不意味着又检测到了猫。

真实验收先让单只猫在画面内形成稳定状态，再观察转身/短暂遮挡：短于 3 秒时动画保留且提示短暂丢失，超过 3 秒出现确认提示，持续离开超过窗口才显示不可见。恢复后提示应清除。另测多猫同时出现与摄像头断流，不允许旧活动状态盖过不确定性或离线。阈值是当前初始策略，后续用真实样例调整，不代表已解决长时间遮挡或身份识别。
