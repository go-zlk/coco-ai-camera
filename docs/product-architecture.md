# 端侧 AI 视觉产品 · 技术架构拆解（服务 / 进程层级）

> 从 [architecture.md](architecture.md) 的高层架构，往下钻到「具体跑哪些进程、用什么技术栈、进程之间怎么通信、完整产品还差哪些东西」。
> 目标：不是 demo，而是一套能部署、能远程管理、能规模复制的**完整产品**。

---

## 0. 先定义「产品」是什么

**一句话**：一台由 Jetson Orin Nano 驱动的端侧 AI 视觉盒子——把「摄像头采集 → 端侧推理 → 结构化事件 → 实时预览 / 告警 / 回放」做成可部署、可远程管理、可批量复制的产品。

**为什么是这个形态**：AI 推断放到**现场**，只回传**结构化结果**（检测框 + 目标类型 + 置信度 + 时间戳），不回传原始视频。换来四点——

| 收益 | 说明 |
|---|---|
| 省带宽 | 原始视频 10 Mbps vs 事件 JSON 几 KB/s，差 4 个数量级 |
| 省云端算力 | 每台设备自带 GPU，云端只存结果，不做视频推理 |
| 隐私友好 | 原始画面不出设备，只出「结论」 |
| 低延迟 | 推理在本地，无需上行往返，检测到告警可在 100ms 内触发 |

这正好是「**把 AI 可靠地落地到资源受限设备**」的完整物化，也是你嵌入式经验（Linux/C/OTA/功率）与 AI 能力的结合点。

**三端形态**：

```
┌─────────────┐         ┌──────────────┐         ┌──────────────┐
│  设备端      │  MQTT   │   云端        │  HTTPS  │  客户端       │
│  Jetson 盒子 │◄───────►│  控制面+数据面 │◄───────►│  App / Web    │
│  (9 个服务)   │  gRPC   │  (8 个服务)   │  WSS    │  (2 端)       │
└─────────────┘         └──────────────┘         └──────────────┘
```

## 2. 设备端：进程/服务深度拆解（核心）

> 这是你 4 年经验的真正用武之地。下面每个服务都按「职责 / 技术栈 / 内部结构 / 对外接口 / 关键实现点 / 为什么这么选」展开。

### 2.1 `edge-vision` — 主推理进程（你正在写的 infer.py 就是它的雏形）

- **职责**：整个产品的核心。摄像头采集 → 预处理 → TensorRT 推理 → 后处理 → 把检测结果（结构化）分发给下游（显示/流/上报）。
- **技术栈**：
  - 采集：GStreamer `nvarguscamerasrc`（CSI）或 `v4l2src`（USB），全程 `memory:NVMM` 零拷贝。
  - 推理：TensorRT engine（`trtexec` 从 ONNX 构建的 FP16/INT8）；前端用 `ultralytics.YOLO` 或直接 `pycuda` 调 TRT runtime。
  - 前后处理：OpenCV（`cv2.cuda` GPU 版）或 cupy，避免 CPU 拷贝。
  - 结果序列化：Protobuf / FlatBuffers（结构化检测结果）。
  - 结果分发：ZMQ `PUB/SUB`（带共享内存），或 GStreamer `appsink` + `interpipe`。
- **内部线程模型**（三阶段流水线，对应 `t_capture / t_infer / t_draw`）：

```
capture 线程 ──► 有界队列(2) ──► infer 线程池(1-2) ──► 有界队列(2) ──► post/draw 线程
   (GStreamer)    (丢帧策略)      (TensorRT)          (背压)         (标注/分发)
```

  - 有界队列 + 丢帧策略：推理跟不上就丢最新帧（不要堆积延迟）。
  - 背压：下游消费慢时，draw 线程阻塞而非无限缓冲。
- **对外接口**：
  - 输出 topic `frame.detect`（ZMQ）：`{frame_id, ts, boxes[{cls, conf, x,y,w,h}], t_capture, t_infer}`。
  - 控制 socket（Unix domain）：`{set_roi, set_threshold, set_model}`。
- **关键实现点**：
  - **零拷贝是命门**：NVMM buffer 从采集到推理到编码全程不走 CPU 内存，否则 1080p@30 会直接把 CPU 打满。
  - **批处理 vs 延迟**：单帧延迟优先（告警要快），batch=1；吞吐优先时才 batch>1。
  - **三段计时**：`t_capture / t_infer / t_draw` 分开打点，`t_infer` 再拆 H2D / compute / D2H（trtexec 出细粒度），这就是 README 里那张量化表的来源。
- **为什么这么选**：Python 快速迭代（你的 infer.py 已经在这么做）；热路径（采集/编码/推理）已经由 GStreamer/TensorRT 的 C 实现扛着，Python 只做胶水，性能不会成为瓶颈。

### 2.2 `edge-stream` — 视频流 + 事件录像

- **职责**：实时预览（低延迟） + 检测到目标时触发录像分片。
- **技术栈**：
  - 流：RTSP（GStreamer `rtsp-server` 或 `mediamtx`）给局域网/设备本地预览；WebRTC（`webrtcbin`）给移动端低延迟。
  - 编码：NVENC 硬件编码 `nvv4l2h264enc`（CPU 几乎零开销）。
  - 录像：检测到目标 → 触发 mp4 分片（`splitmuxsink`，按时间/大小切），带事件元数据。
- **内部结构**：与 `edge-vision` 共享 NVMM 帧（通过 GStreamer `tee`），不是另起一路采集——一路采集，多路分发。
- **关键实现点**：
  - 预览用 H.264 低延迟档（`zerolatency` tune），录像用高画质档，两路编码参数不同。
  - 事件录像要**前置缓冲**（pre-roll 5s），否则告警瞬间之前的画面会丢。
- **为什么这么选**：NVENC 是 Jetson 硬件编码器，省出 CPU/GPU 给推理；`tee` 复用采集，避免双路采集浪费传感器带宽。

### 2.3 `edge-telemetry` — 遥测/事件上报

- **职责**：把设备指标 + 业务事件上报云端。
- **技术栈**：
  - 采集：解析 `tegrastats`（GPU/CPU/内存/温度/功耗）+ 从 `edge-vision` 订阅业务指标（FPS/延迟/检测数）。
  - 传输：MQTT over TLS（QoS 1）或 gRPC；序列化 Protobuf（你的强项）。
  - 本地缓冲：SQLite WAL，断网时落盘，恢复后补传（保证不丢事件）。
- **关键实现点**：
  - **分级**：指标类（可丢，QoS 0）与事件类（不可丢，QoS 1 + 落盘补传）分开。
  - **节流**：指标 10s 一次；事件实时。避免遥测反噬推理。
  - **为什么这么选**：MQTT 轻量、支持弱网、天然 pub/sub；Protobuf 适合设备间的稳定通信和版本演进。

### 2.4 `edge-config` — 配置管理

- **职责**：本地配置 + 远程下发 + 动态生效。
- **技术栈**：本地 YAML/JSON + 校验（jsonschema/pydantic）；远程订阅 MQTT 配置 topic 或 gRPC stream。
- **关键实现点**：
  - 配置分层：**设备级**（分辨率/模型） vs **云端下发**（ROI/阈值） vs **运行时**（临时）。
  - 云端下发走 retained message，设备上线即拿到最新配置。
  - 变更通过控制 socket 通知 `edge-vision` 动态热加载（不重启进程）。
- **为什么这么选**：配置是最容易出「现场事故」的地方，必须有校验 + 回滚（改坏了能退回）。

### 2.5 `edge-ota` — 固件 + 模型升级（你的 OTA 强项，重点打磨）

- **职责**：固件（系统）与模型（.engine 文件）的可靠升级 + 自动回滚。
- **技术栈**：
  - 系统固件：**A/B 分区**（rootfs A/B），用 NVIDIA L4T OTA 工具（`l4t_ota_tools`，image-based OTA）或 Mender/RAUC。
  - 模型/应用：轻量级 artifact 下发（engine + SHA256 校验 + 版本号）。
- **关键实现点**：
  - **原子切换**：新分区写好校验通过后，bootloader 一次性切换，绝不半新半旧。
  - **自动回滚**：启动失败计数（`bootcount`）→ 超过阈值 → 硬件 watchdog 触发 → 回滚到旧分区。
  - **灰度**：先推 1% 设备 → 看遥测（崩溃率/内存/延迟）→ 逐步放量 → 有问题一键回滚。
  - **模型热切换**：换 engine 不换系统，`edge-vision` 重载即可，秒级生效。
- **为什么这么选**：A/B + 签名 + 自动回滚是工业级 OTA 的三要素，你在无人机/相机里做过，这里直接复用叙事。

### 2.6 `edge-monitor` — 本地监控 + watchdog

- **职责**：进程存活监控 + 异常自愈 + 崩溃现场抓取。
- **技术栈**：systemd `WatchdogSec`（软）+ Tegra 硬件 WDT `tegra_wdt`（硬）；崩溃抓 core dump 上报。
- **关键实现点**：
  - **三层看护**：systemd 管进程重启 → 应用喂软狗 → 硬件狗管内核假死。
  - 假死检测：推理进程 OOM/卡死 → 心跳超时 → 重启进程 → 连续失败 → 回滚固件。
  - 崩溃现场：`/proc/pid` + `dmesg` + core dump 打包上报云端，便于远程定位。
- **为什么这么选**：现场设备没人看着，必须能自愈 + 留下可诊断的「尸体」。

### 2.7 `edge-power` — 功率管理

- **职责**：功率域切换 + 动态调频，在性能与功耗/散热间平衡。
- **技术栈**：`nvpmodel`（多档功率域，7W/10W/15W，JetPack 6 的 SUPER 模式可达 25W）+ `jetson_clocks`（固定最高频）+ 自定义动态策略。
- **关键实现点**：
  - **场景化策略**：常驻监控用 7W 低功耗档；检测到目标/录像时切 15W 满频。
  - **温度保护**：Tegra 温度超阈值 → 降频/降功率档，防止热失控（户外设备关键）。
  - 数据来源：`tegrastats` 的功耗/温度，形成「功率-性能-温度」闭环。
  - **为什么这么选**：8GB 共享内存和功率域提供了清晰的资源约束，便于量化性能、功耗与温度之间的取舍。

### 2.8 `edge-sync` — 数据同步 / 本地存储

- **职责**：录像/事件的本地持久化 + 上行同步 + 保留策略。
- **技术栈**：本地 NVMe SSD；上行 S3/MinIO（分段上传 + 断点续传）；保留策略（本地保留 7 天，云端长期）。
- **关键实现点**：
  - 事件优先、录像懒传（实时传事件 JSON，录像在空闲/夜间批量上行）。
  - 空间满 → 按优先级删除最旧录像（保事件不保录像）。
- **为什么这么选**：存储是成本大头，必须分级 + 懒传 + 保留策略。

### 2.9 `edge-identity` — 设备身份 + 安全

- **职责**：设备唯一身份、安全启动、通信加密。
- **技术栈**：安全启动（PKC/SBK fuse）+ X.509 设备证书 + OP-TEE 存私钥。
- **关键实现点**：
  - **一次性 provisioning**：首次上电生成密钥 → 云端注册 → 签发设备证书 → 后续 mTLS。
  - 私钥不落盘明文（存 TEE/TPM），防现场拆机提权。
  - 固件/模型下载前验签（SHA256 + ECDSA）。
- **为什么这么选**：安全启动 + 设备证书是「能卖给企业客户」的门槛，也是区别于纯 demo 的关键。

### 2.10 设备端 IPC 与数据通路（帧的零拷贝流转）

```
                摄像头 (CSI/USB)
                      │ nvarguscamerasrc (memory:NVMM)
                      ▼
              ┌─── edge-vision ───┐
              │ capture → infer → │
              └──────┬────────────┘
                     │ tee (NVMM 零拷贝)
          ┌──────────┼──────────────┐
          ▼          ▼              ▼
    edge-vision     edge-stream    (其他消费者)
    结果分发 ZMQ    预览/录像 NVENC
```

- **帧传输**：ZMQ + **共享内存**（`/dev/shm` 或 DMA-BUF fd 传递），不序列化不拷贝。
- **控制面**：Unix domain socket / gRPC（小数据、低频）。
- **配置/状态**：SQLite + 文件。
- **关键原则**：**大帧走共享内存/零拷贝，小消息走 socket**。这是嵌入式里最容易被忽略、也最能体现功力的一条。

### 2.11 设备端资源预算（8GB 共享内存，初版估算 → 实测校准）

> 数字先给量级，实际以 `tegrastats` 实测为准（这正是 README「数字从哪来」的延续）。

| 项 | 预算 | 说明 |
|---|---|---|
| OS / JetPack | ~1.5–2 GB | L4T + 桌面/服务 |
| 帧缓冲 (NVMM) | ~0.3–0.5 GB | 720p/1080p 几帧 + 队列 |
| TensorRT engine + workspace | ~1–2 GB | 取决于模型大小/精度 |
| 编码器缓冲 | ~0.5 GB | NVENC 输出 |
| 各进程运行时 | ~0.5 GB | 9 个服务 |
| **余量** | **~1.5–2 GB** | 留给突发/大模型 |

**GPU 算力**：Ampere 1024 核，推理占大头；NVENC/PVA 分担编码与部分视觉预处理，别让 CPU 抢 GPU 的活。

## 3. 云端：服务分解

> 云端不是你的主战场，但「知道边界、能和后端对齐」是端侧工程师升维的关键。这里点到关键设计，不展开到代码。

### 3.1 设备接入网关
- **技术栈**：EMQX（云）或 Mosquitto（小规模）。
- **要点**：mTLS 双向认证；设备连接状态（online/offline）维护；消息路由到下游（Kafka/Redis stream）。

### 3.2 设备注册中心
- **技术栈**：Go + PostgreSQL。
- **要点**：设备 ID、型号、固件/模型版本、归属租户、地理位置；设备生命周期（激活/注销/转移）。

### 3.3 遥测/时序
- **技术栈**：网关 → Kafka/Redis Stream → TimescaleDB（Postgres 时序扩展，小团队够用；量大换 InfluxDB/VictoriaMetrics）。
- **要点**：指标按设备 ID 分片；聚合 + 下采样；告警规则引擎（阈值/趋势/异常检测）。

### 3.4 事件/媒体存储
- **技术栈**：事件元数据 Postgres（按 `device_id + ts + cls` 建索引，检索「某设备某时段出现某人」）；文件 S3/MinIO。
- **要点**：结构化检索是核心卖点——「回放不是翻视频，是查数据库」。

### 3.5 模型/固件管理与 OTA 下发
- **技术栈**：Go + S3（artifact 存储）+ 版本注册表。
- **要点**：签名；灰度策略（按租户/设备分组/比例）；下发结果回执 → 回滚决策。

### 3.6 用户/鉴权
- **技术栈**：Keycloak（OIDC/OAuth2）或 Auth0。
- **要点**：RBAC（管理员/操作员/只读）；设备归属（tenant）隔离。

### 3.7 API 网关 + 实时推送
- **技术栈**：Go/Node REST + WebSocket/SSE（或 EMQX 的 MQTT-over-WebSocket 直连客户端）。
- **要点**：事件实时推给在线客户端；离线期间事件存收件箱，上线补推。

### 3.8 告警/通知
- **技术栈**：规则引擎触发 → APNs/FCM 推送 + 邮件 + Webhook。
- **要点**：去重/静默窗口（同一目标 5 分钟不重复告警）；告警确认与升级。

## 5. 模型与数据闭环（MLOps）

> 产品上线后，「能不能持续变好」取决于这条闭环。这是你从「会跑 demo」到「懂产品」的分水岭。

```
① 数据采集 ──► ② 标注 ──► ③ 训练 ──► ④ 量化 ──► ⑤ 评估 ──► ⑥ 下发 ──► ⑦ 监控 ──► 回到 ①
  端侧难例回传   半自动预标  云端 GPU   PT→ONNX→TRT  mAP+延迟回归  OTA 灰度   漂移检测→再训练
```

- **① 数据采集**：端侧把**难例**回传（低置信度 0.4–0.6、误检、漏检的用户反馈），不是全量视频。
- **② 标注**：先用现模型预标，人工审核（半自动），降低标注成本。
- **③ 训练**：云端 GPU（或 Colab/租卡），YOLO 微调。
- **④ 量化**：`yolo export` → ONNX → `trtexec --fp16/--int8`（INT8 需校准集）。这是你 PLAN.md D8-9 的内容。
- **⑤ 评估**：精度（mAP 回归，不能掉）+ 延迟（trtexec 回归，不能涨）。
- **⑥ 下发**：OTA 灰度，回执监控。
- **⑦ 监控**：端侧指标回传 → 数据漂移（分布变了）→ 触发再训练。

## 6. 横切关注点

| 关注点 | 设备端 | 云端 |
|---|---|---|
| **安全** | 安全启动、PKC、TEE 存私钥、固件/模型验签 | mTLS、OIDC、RBAC、租户隔离 |
| **可观测** | journald → 集中日志；Prometheus 指标；OpenTelemetry 追踪 | 集中日志、监控告警 |
| **CI/CD** | 固件 CI（构建+签名）、模型 CI（训练+量化+评估） | 服务 CI/CD |
| **测试** | 单元 + 集成 + **硬件在环 HIL**（真实板子 + 真实摄像头跑回归） | 集成/e2e |

**HIL 硬件在环**是你嵌入式背景的差异化卖点：模型/固件每次变更，在真实 Jetson + 真实摄像头 + 固定测试视频上跑一遍，自动出「FPS/延迟/内存/温度」回归报告，挡住「训练集涨分、现场掉链子」。
