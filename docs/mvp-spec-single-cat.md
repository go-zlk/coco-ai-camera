# 单猫状态桌宠 MVP

实施入口：[软件开发指引](software-development-guide.md)、[任务与依赖清单](development-backlog.md)、[MVP 软件实现架构图](diagrams/mvp-software-architecture.html)。指引细化内部 unknown、客户端失联、崩溃恢复及两周投入假设；下文性能目标均需实测。

## 目标

在 Jetson Orin Nano 上持续接入一台摄像头，判断一只猫当前属于四种状态之一，并让网页桌宠在局域网内同步显示，同时保存当天的状态时间线。

MVP 的价值证明是：上班族打开网页，用一眼知道“猫现在是否在活动、是否在休息、是否暂时看不见、设备是否离线”，并能回看当天各状态持续了多久。

## 固定范围

输入固定为一台摄像头、一个视频源和一只猫。首选 CSI 或 USB；RTSP 只在已有稳定地址时接入。Jetson 负责采集、推理、状态机、存储和 API；浏览器负责桌宠动画与时间线展示。

四个状态的定义：

| 状态 | 定义 | 桌宠表现 |
|---|---|---|
| 活动 active | 猫被稳定检测到，时间窗口内有明显位移或活动证据 | 走动、眨眼或轻微摇尾 |
| 休息 resting | 猫被稳定检测到，连续窗口内低位移 | 躺下或睡觉 |
| 不可见 out_of_view | 摄像头在线，但超过阈值没有检测到猫 | 从门后走出并暂时隐藏 |
| 离线 offline | 摄像头断流、输入超时或服务无法取得新帧 | 显示连接异常和最后更新时间 |

另设内部 `unknown` 作为保护状态：画面质量差、置信度不足或状态证据冲突时使用。网页可以将它显示为“正在观察”，但它不计入四种业务状态的活动时长。

状态必须经过时间窗口、防抖和最短保持时间后才能切换。例如单帧漏检不能立即触发“不可见”，短暂断流不能立即触发“离线”。

## 最小技术实现

1. 在现有 `infer.py` 的输入路径上增加稳定采集循环、有界帧队列、断流重连和 headless 模式。
2. 使用一个轻量猫检测模型；先采用检测框中心位移和连续窗口规则区分 `active`/`resting`，不引入复杂行为识别模型。
3. 建立状态机：输入检测结果和连接健康度，输出状态变更事件。
4. 使用 SQLite 保存状态区间和事件。每条区间至少保存开始时间、结束时间、状态、置信度、摄像头 ID 和模型版本。
5. 提供三个接口：当前快照、当天时间线、WebSocket 状态变更。浏览器断线后先取快照，再订阅增量事件。
6. 写一个网页桌宠：四种状态对应四套动画；时间线用色带或列表展示当天区间；标明“最后观察时间”。
7. 用 systemd 或等价脚本让服务开机启动，日志中记录断流、重连、状态切换、推理耗时和丢帧数。

## 两周计划

### 第 1—2 天：冻结环境和输入

记录 JetPack、TensorRT、OpenCV/GStreamer 版本；确认摄像头管线可连续运行。保存一段白天和一段夜间样例视频，建立可重复的离线回放命令。

验收：摄像头连续运行 30 分钟；断开再接入后能恢复；无显示模式可运行。

### 第 3—4 天：检测和基准

固定一个模型版本，测量端到端 FPS、P50/P95 延迟、显存、内存、温度和功耗。修正当前脚本中 `--device` 未真正传入、CPU BGR 路径被误称为零拷贝等问题。

验收：同一视频可重复得到检测结果和基准报告；README 不再使用未实测的占位性能数字。

### 第 5—7 天：四态状态机

实现轨迹缓存、活动阈值、休息阈值、不可见超时、离线超时、恢复逻辑和 `unknown` 保护状态。用录制视频和人为断流测试边界。

验收：单帧漏检不切状态；断流显示离线；摄像头在线但猫离开视野显示不可见；恢复后回到正确状态。

### 第 8—9 天：事件和时间线

实现 SQLite schema、状态区间合并、事件 ID 去重和日报统计。重启服务后继续写入，避免重复累计区间。

验收：重启、重复事件和跨午夜场景都能得到正确时间线；未知区间不被伪装成活动或休息。

### 第 10—11 天：网页桌宠

实现当前快照、WebSocket 订阅和四套状态动画。浏览器断线后自动重连，进入页面立即显示最新状态和更新时间。

验收：模拟事件可以独立驱动动画；真实摄像头状态和动画状态一致；手机浏览器在同一局域网可打开。

### 第 12—13 天：设备化运行

加入 systemd 启动、日志轮转、配置文件和健康检查。记录丢帧、推理耗时、队列长度、温度和断流次数。

验收：服务崩溃后自动拉起；摄像头恢复后自动恢复；运行 12 小时无持续内存增长。

### 第 14 天：演示和证据

录制一段完整演示：猫活动 → 休息 → 离开画面 → 摄像头断开 → 恢复。整理准确率、状态切换延迟、FPS、P95、功耗和失败案例。

验收：别人只看 README 和演示即可复现；所有性能数字带有硬件、分辨率、模型和功耗模式条件。

## MVP 验收指标

- 状态切换在目标窗口结束后 5 秒内反映到网页。
- 摄像头断流在 10 秒内显示 `offline`，恢复后 15 秒内恢复推理。
- 连续运行 12 小时无崩溃、无持续内存增长。
- 当天时间线可查询，重启不丢失已提交区间。
- 离线、不可见、unknown 不混为同一状态。
- 记录至少一份模型精度和一份板端性能报告；指标不使用估算值。

## 明确不做

- 不做多猫识别、猫脸识别、跨摄像头 ReID。
- 不做“真实情绪”或健康诊断；活动/休息只是视觉可观察状态。
- 不做可靠的睡眠、进食、玩耍等细粒度行为识别；这些属于下一阶段数据和模型问题。
- 不做小米生态的通用接入；只验证一个明确支持 RTSP/ONVIF 的来源。小米型号兼容性单独评估。
- 不做云端视频上传、远程公网暴露、账号体系、支付和社交功能。
- 不做原生 Windows/macOS/iOS/Android/Watch 客户端；先用响应式网页验证产品价值。
- 不做多摄像头融合、摄像头云台控制、语音交互和自动投喂硬件。
- 不做 DeepStream、ROS 2、复杂时序网络或 INT8 优化作为首版前置条件。
- 不把未校准的 INT8 engine、未经实测的零拷贝或估计 FPS 写成项目成果。

## MVP 完成后的下一步决策

只有在单猫四态版本完成并有数据后，才根据实际问题选择方向：

- 误把静止当休息：增加姿态或时序模型。
- 不可见误报多：增加区域、背景和摄像头布置约束。
- 多猫需求真实存在：加入 ReID 和身份标注。
- 用户每天确实查看时间线：增加手机通知和原生桌面挂件。
- 性能或功耗不足：再评估 CUDA/NVMM、TensorRT engine 和 DeepStream。
