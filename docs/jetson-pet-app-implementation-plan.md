# Jetson Orin Nano：真实猫咪 → 虚拟宠物

本文件描述目标架构与实施顺序，不代表已部署完成。架构图见 `diagrams/pet-edge-ai-architecture.html`。当前仅根据仓库代码审查，未连接实体 Jetson 验证。

## 产品闭环与部署边界

家中摄像头 → Jetson 解码、检测、跟踪、行为判断 → 状态事件与时间线 → 电脑桌宠。首版限定单摄像头、单猫、局域网网页桌宠；远程同步和原生桌面挂件随后增加。

Jetson 常驻家中，承担视觉推理、状态判断、本地存储和服务。手机、电脑、手表负责呈现，不各自重复视频推理。图中的同步 API 是逻辑访问边界：首版服务直接运行在 Jetson；外网访问阶段增加私有网络或经过鉴权的中继，不直接暴露摄像头或无鉴权接口。

图中“模型实验室”表示板端部署、引擎构建和评测部分；数据标注与模型训练可在开发电脑或云端完成。ONNX 是交换格式，TensorRT engine 在目标软硬件环境构建、验证并版本化。运维模块位于板端，并不意味着必须采购云服务。

## 当前工程与缺口

| 已有代码 | 当前能力 | 下一步必须补齐 |
|---|---|---|
| `infer.py` | 摄像头/视频输入、YOLO 推理、画框、简单基准 | 无显示服务模式、重连、跟踪、状态判断、结构化输出 |
| `scripts/build_engine.sh` | 导出 ONNX，调用 trtexec 构建与评测 | 目标环境兼容性、精度回归、可信 INT8 校准或 Q/DQ 流程 |
| `scripts/power.sh` | 调用功耗模式与 tegrastats | 读取设备实际模式定义，记录温度、功耗与性能变化 |
| README 中性能表 | 待填结果模板 | 实测数据、完整运行条件与可复现命令 |

代码审查中发现：CSI 管线最终转换为 CPU BGR，不能称为端到端 GPU 零拷贝；`--device` 尚未传入模型调用；视频读取失败后主循环退出；显示路径不适合无头常驻服务。`build_engine.sh` 实际调用无校准信息的 `--int8`，不能据此宣称 INT8 精度可信。`requirements.txt` 未锁版本，安装 OpenCV 后应检查 GStreamer 支持。以上属于待改进项，本次没有修改运行代码。

## 实施顺序与验收

### 1. 固定板端环境

记录准确板型、内存容量、JetPack/L4T、CUDA、TensorRT、Python 和 OpenCV 版本；确认存储余量、散热、电源、网络与系统时间。以板端实际兼容组合为准，不直接将开发电脑上的依赖或 engine 复制过去。

可采集的诊断命令：

```bash
cat /etc/nv_tegra_release
uname -a
dpkg-query -W nvidia-jetpack 'libnvinfer*'
gst-inspect-1.0 nvarguscamerasrc
gst-inspect-1.0 nvv4l2decoder
python3 -c 'import cv2; print(cv2.getBuildInformation())'
sudo nvpmodel -q --verbose
```

部分组件未安装时命令会报告缺失，这也是环境记录。不要假定功耗模式编号在不同版本中含义相同。

**验收：**保存环境清单；通过 SSH 可启动一次无显示推理；确认输入、模型和依赖都可重复运行。

### 2. 打通稳定的视频输入

先选择一条已验证输入：现有 CSI/USB 摄像头，或明确提供 RTSP 的网络摄像头。配置项统一 source、分辨率、帧率、超时与凭据。实现有界帧队列、时间戳、旧帧丢弃与断流重连，避免处理越来越旧的视频。

小米摄像头必须按具体型号和固件验证，不能假定米家设备都提供 RTSP/ONVIF。go2rtc 的 Xiaomi 接入仅覆盖部分型号，并有联网获取密钥等约束，应作为可选适配器，不成为首版阻塞依赖。

**验收：**持续输入，并通过断网/恢复测试；摄像头离线能够单独报告。暂不为了远程预览增加视频重编码；Orin Nano 没有 NVENC 硬件编码器。

### 3. 检测、跟踪与行为状态

先用小型检测模型找到猫，结合跟踪减少帧间跳动。检测到猫只证明目标存在，不能单靠检测框判定睡眠、进食或情绪。

初版分别维护两个维度：

- 连接状态：online / offline / stale。
- 可观察行为：active / resting / out_of_view / unknown。

行为依据包括连续时间窗口中的位移、姿态、检测可信度及可选区域。低运动只能先标为休息或疑似睡眠；进食需要动作、食盆区域及标注数据支持。加入进入/退出阈值、最短保持时间和防抖。摄像头离线时显示离线，不能把它映射成猫走出画面。

**验收：**建立自己家中白天、夜间、遮挡和空画面的测试集；按独立视频片段划分训练/验证/测试，避免相邻帧泄漏。报告各状态 precision/recall、混淆矩阵、unknown 比例、状态转换延迟和误切换次数。多猫身份识别留到下一阶段。

### 4. 事件、时间线与服务接口

首版使用进程内事件通道与 SQLite，不必立刻引入 Kafka 或多个微服务。保存状态区间、置信度、最后观察时间及模型版本；日报按区间时长统计，同时展示不可见/未知时长，不能把可见时段外推成全天活动比例。

状态事件建议包含：

```json
{
  "schema_version": 1,
  "event_id": "unique-id",
  "device_id": "home-jetson",
  "camera_id": "living-room",
  "pet_id": "cat-1",
  "observed_at": "2026-09-04T04:00:00Z",
  "connectivity": "online",
  "behavior": "resting",
  "confidence": 0.86,
  "model_version": "pet-v0.1"
}
```

提供当前快照、按日时间线的 HTTP API，以及状态变更 WebSocket。客户端重连先取快照；用事件 ID 去重；过期数据显示最后更新时间。设置数据保留期限，默认发送状态，不上传连续原始视频。

**验收：**重启后历史仍在；离线不误显示实时；重复事件不会重复累计时间。

### 5. 让桌宠与真实状态同步

先做浏览器客户端验证动画与情绪价值：active → 走动，resting → 休息，out_of_view → 走出门，offline/stale → 连接提示。动画过渡由客户端状态机控制，避免检测抖动导致频繁切换。

随后包装成桌面常驻应用，再做手机端；手表先展示最近状态和更新时间，刷新方式服从平台后台限制，不承诺持续实时连接。

**验收：**旁观者可以从真实视频、事件和动画同时观察到一致变化；模拟事件可独立驱动客户端，方便调试与录制演示。

### 6. 做成可长期运行、可证明能力的项目

使用 systemd 管理进程、自动拉起、启动依赖和日志轮转。容器可作为后续可复现交付方式，基础镜像需匹配 Jetson 软件栈。配置、模型、应用分别版本化，更新先健康检查，失败能回到上一版本。

Flight Recorder 记录采集到客户端显示的端到端延迟、各阶段耗时、处理帧率、队列丢帧、断流次数、内存、温度与功耗。区分模型推理基准与整个产品延迟；GPU 异步操作须采用正确同步或 CUDA 事件计时。

**验收：**72 小时运行报告，覆盖摄像头断连、网络恢复、进程崩溃与服务重启；附模型精度报告、性能条件、复现说明及失败案例。72 小时是计划验收目标，不是已完成结果。

## 建议的第一个里程碑

“单摄像头 + 单猫 + Jetson FP16 推理 + 休息/活动/不可见/未知 + 离线识别 + 网页桌宠 + SQLite 日时间线”。完成后用实测决定是否优化 CUDA/零拷贝、加入复杂时序模型或接入 DeepStream。无需把学习整套 NVIDIA 生态作为启动项目的前置条件。

面试背书应呈现：需求取舍 → 数据与评测 → 部署与性能 → 故障恢复 → 可运行演示，而不仅是检测模型画框截图。
